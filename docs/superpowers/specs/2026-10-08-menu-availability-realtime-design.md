# Issue #441：菜單供應狀態即時更新（方案 B）

日期：2026-10-08（Asia/Kuala_Lumpur）

Issue：https://github.com/erictheng93/Makan-Masak/issues/441

## 目的與決策

使用者已選擇方案 B：正在瀏覽菜單的顧客，以及已開啟的後台與廚房，
能收到同一家餐廳的售完／恢復供應更新，不必手動重新整理。
沿用現有 WebSocket、RealtimeSession、廣播服務與前端查詢機制。

顧客菜單目前只列出可供應菜品。此行為維持：售完項目移除，恢復供應
項目重新出現。公開訂閱只能取得菜單變更資訊，不取得訂單、桌台、
群組購物車、員工資料或內部庫存警示。

## 現有流程與修改範圍

- 單筆 `PUT /api/v1/menu/items/:id` 經 API MenuService 進入資料庫 MenuService。
- 批次 `PATCH /api/v1/menu/:restaurantId/items/availability` 也經這兩層。
- 經理動作 `update_menu_availability` 在 ManagerActionsService 直接寫資料庫，
  須改用同一套菜單更新與快取失效流程，保留操作代理與稽核紀錄。
- `broadcastMenuAvailabilityUpdate` 目前只投遞到 `admin:{restaurantId}`，
  無呼叫者；改為確實連接上述寫入流程，並投遞到現有廚房房間。
- 顧客新增 `menu:{restaurantId}` 房間；現有訂單、桌台與群組房間維持其
  原有授權邊界，不列舉或逐一喚醒那些房間。

服務共用寫入後的通知邏輯，避免三個入口各自組裝不同事件。
廣播發生於成功寫入及快取失效之後。寫入失敗不通知；同值重送不產生
新的供應狀態事件。單筆 `isAvailable` 或 `inventoryCount` 實際改變時通知；
批次依成功更新且實際改變的項目通知，重複 ID 不重複通知。
經理動作的查詢與寫入都必須限定請求餐廳，跨餐廳與已刪除菜品不得修改。

本次不涵蓋下單扣庫存、退單補庫存的每次庫存變動，也不改變伺服器下單
可用性檢查；驗收範圍是 issue 列出的三個供應設定入口。

## 公開訂閱與安全邊界

新增 `POST /api/v1/realtime/auth/menu-token`，接受 `restaurantId`。
沿用公開菜單的餐廳判定：餐廳存在、啟用且未刪除，才簽發短效 token。
桌邊、店面、登入或未登入顧客都可訂閱，因為菜單本身已公開。

Token 固定使用專屬 `menu-realtime` scope，`roomType: menu`，
`roomId` 與 `restaurantId` 相等，五分鐘到期。其授權不能兌換或進入
`customer`、`admin`、`kitchen` 房間；那些房間的 token 也不能直接進入
菜單房間。Worker 和 DO 都驗證 scope、簽章、到期與房間綁定。

簽發端沿用公開 realtime token 端點每 IP 每分鐘 10 次的限流。
握手沿用 Worker 層 IP 與客戶端兩層限流，拒絕請求在接觸 DO 前終止。
公開客戶端限流以 IP 和餐廳建立穩定的 bucket，不讓重簽 token 重置
bucket，也不讓整家餐廳的顧客共用單一匿名客戶端 bucket。
此 bucket 用於限流，不能作為身分或存取權限證明。

DO 對菜單房間使用明確的事件允許清單，先於任何群組事件捷徑或角色
判定；僅允許同餐廳的公開菜單變更事件與必要連線控制訊息。
匿名菜單訂閱不接受任意 subscribe 訊息來擴張事件範圍。

公開通知沿用 `MENU_ITEM_UPDATE` 的最小資料 `{ menuItemId, action: updated }`，
作為重新查詢訊號，不攜帶 `menuItem`、菜品名稱、庫存或操作原因。
只有未刪除且分類可公開的菜品會產生公開通知，售完狀態不阻擋通知。
後台與廚房沿用 `MENU_AVAILABILITY_UPDATE`，取得名稱、供應狀態與庫存。

## 前端行為

### 顧客

`MenuView.vue` 與 `ShopMenuView.vue` 沿用 `useWebSocket` 連線機制，
透過一個共用 composable 訂閱目前餐廳。第一次連線建立、收到菜單變更、
以及斷線重連成功時，重新查詢該餐廳的公開菜單。
短時間多個事件合併查詢，沿用既有查詢快取與去重能力。
以最新回應取代菜單資料，不因晚到事件將狀態改回舊值。

Token 過期時按既有有上限的重連流程重新取得 token。
離開頁面或切換餐廳時關閉舊訂閱、取消重試，避免舊餐廳回應覆寫新頁面。
即時連線失敗時保留現有瀏覽與 REST 下單流程。
已加入購物車的項目不靜默刪除，仍由現有下單驗證提示可用性問題。

### 後台

沿用 `admin:{restaurantId}` 連線及現有菜單警示面板。
`useMenuManagement` 收到供應變更時刷新菜單清單，使卡片狀態與通知一致。
刷新保留正在編輯的表單；既有 `updatedAt` 衝突檢查繼續保護儲存。
重連成功後也刷新，以補回斷線期間漏掉的變更。

### 廚房

沿用 `kitchen:{restaurantId}` 連線，在 `EnhancedKitchenDashboard.vue`
訂閱供應事件，使用既有提示元件顯示菜品名稱及售完／恢復供應狀態。
增加必要的六語系文案，遵守 DESIGN.md、設計 token 與基本可及性。
廚房目前沒有菜單清單，本次不增加菜單管理頁，也不改寫既有訂單內容。
廚房提示屬於當下通知；斷線期間的歷史提示不重播。

## 一致性、失敗與成本

寫入成功不因 best-effort 廣播失敗而回報寫入失敗，沿用現有廣播錯誤紀錄。
快取清除後的查詢須讀到最新供應狀態；若仍有其他 API 回應快取，須一併
失效，不能讓收到通知的顧客重新讀到舊快取。
初次接上連線也刷新，以補足初始查詢與訂閱建立之間的競態。

每個有變更的公開菜品至多投遞到菜單、後台、廚房三個房間；批次公開
通知可合併為一個受影響公開菜品的刷新訊號，後台／廚房保留各菜品狀態。
不增加定時輪詢、事件歷史、DO alarm、持久重試佇列或新依賴。
沒有聽眾仍可能有單次廣播喚醒費用；以實際變更、批次合併與有上限重連
控制新增請求量，不建立房間登記系統來追蹤聽眾。

## 驗收與關閉條件

1. 用單筆、批次、經理動作分別執行售完與恢復供應，確認成功寫入、
   快取失效與正確餐廳事件；同值、失敗、跨餐廳、已刪除項目不誤推。
2. 公開 token 測試覆蓋不可用餐廳、scope／房間不符、偽造、過期及限流；
   菜單房間不能收到訂單、群組、桌台或其他餐廳事件。
3. 顧客桌邊與店面菜單同時開啟，售完後菜品移除、恢復後重新出現，
   無須重新整理；分類可見性與公開資料過濾持續生效。
4. 另一台後台的清單與警示面板同步更新；廚房顯示正確供應提示。
5. 顧客與後台斷線期間修改供應，重連後取得最新菜單；離頁／切店停止
   舊連線，連線失敗仍可瀏覽，購物車不被靜默清空。
6. 新增實際 mutation → DO → WebSocket → 客戶端查詢的本地整合驗證，
   並進行跨畫面瀏覽器驗收；mock 單元測試不能單獨證明串接完成。
7. 通過相關測試、型別、lint、格式、palette 與 `pnpm verify`，記錄實際
   指令與結果。依 repository 規則建立原子提交，發布需使用者明確授權。
8. Issue 留下驗收證據及可取得的提交／整合位置後才關閉。
   僅完成本地實作或尚未通過串接驗收時，保持 issue 開啟並記錄剩餘項目。
