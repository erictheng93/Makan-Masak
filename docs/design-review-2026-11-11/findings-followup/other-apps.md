# Other-app findings verification and repairs

Scope: management portal tenant creation, kitchen modal transitions and legacy switch semantics, onboarding success assertions. No commit, push, deployment, production account changes or production business writes were performed by this worker.

## Verdicts

- **CreateTenantModal accidental dismissal: confirmed.** `finish` was shared by Dialog `close`, backdrop, header X and explicit Done, with no pending/result guard. New regression checks failed before the fix: Escape emitted success while the owner setup link was displayed; Escape and Cancel both emitted close while creation was pending. `requestDismiss` now ignores accidental dismissal during submission or the result step. Pending Cancel and the result-step X are disabled; explicit Done still emits the existing success/close event. The setup link is retained in the result until Done. API requests and result handling are unchanged.
- **Kitchen animation regression: confirmed.** Before repair, a real 390px browser sampled 35 frames opening the urgent threshold picker with no active animation, opacity 1 and transform none throughout. The original Settings implementation had an opacity/slide Transition which the Dialog conversion removed. OrderDetails' inner Vue Transitions were removed with Dialog closure, and Confirm's Transition wrapped the portal-based Dialog root. They now use the already-installed Headless UI TransitionRoot/TransitionChild lifecycle, preserving confirmation content during leave. Existing focus containment and Escape remain. After the change, an actual focus regression was found: Headless UI attempted focus restoration while the background was still inert. A shared 20-line `useDialogReturnFocus` captures the actual opener and restores it after leave/nextTick, with connected-element and reopen guards. The existing Settings regression now waits for completed leave before asserting removal and focus.
- **Onboarding SuccessView test assertion: confirmed.** The inbox-only case checked `wrapper.text()` for absence of a translation key that was present only in an aria-label, so it could not detect an incorrectly rendered copy-ID button. It now asserts that exact accessible button is absent. The positive copy-ID test additionally checks the actual `APP-1` value sent to the clipboard and the announced result. No product behavior change was necessary.
- **Five legacy kitchen toggles affected by the shared minimum-size rule: confirmed markup gap.** PerformanceDashboard, PriorityTimingManager, EnhancedShortcutsPanel, WorkflowAutomation and InteractiveStatsPanel used plain button tracks without switch semantics. They now expose role=switch, actual aria-checked and their existing translated accessible names. No toggle handler or feature logic changed. Two service-object properties are nested Refs and are explicitly unwrapped for aria-checked. The shared CSS track-size/hit-area repair is owned by the controller.

### Production QA discovery: Grid filter labels

Confirmed from actual production Chef phone Grid screenshot: global minimum inline size allowed the flex-row status/quick-filter buttons to shrink and clip/overlap their nowrap labels. The local repair adds `[&>button]:shrink-0` to the existing horizontally scrolling row only. This covers all nine status, urgency, quick and takeaway/delivery buttons without changing handlers. Actual local Vue checks at 390×844 and 1440×900 confirm every label fits, all nine buttons activate and show zero-result filtering, the phone row scrolls to the final actionable button, and the page has no horizontal overflow or JavaScript errors. Production RED is `chef-mobile-grid.png`; local GREEN artifacts and checks are `chef-grid-local-*.png` / `chef-grid-local-checks.json` in the visualization production-qa folder. Pending the controller's final deployment, no production GREEN is claimed yet.

### LicensesView Escape and pending submission

**Partly accurate finding.** Escape closed the modal, but the original component retained `generateForm`; reopening did not lose its data. Closing a dirty form without warning was still an interaction problem, and dismissal/duplicate submission while generation was pending was unguarded. The shared close handler now blocks pending dismissal and asks a native translated confirmation before explicitly discarding a dirty draft; pristine close and successful generation proceed normally. The guard is shared by Escape, backdrop and Cancel. Generate and Cancel are disabled during submission, with a duplicate-submit guard. Confirmation text is present in all six supported locales. API paths, generated-license data and success list insertion are preserved.

The browser regression failed before repair because Escape immediately removed a dirty dialog even with discard denied. After repair, the actual component passed denied-discard retention, confirmed discard/reset, pristine dismissal without a confirmation, pending Escape/Cancel/duplicate prevention, and successful completion/visible generated license. All requests in this verification were isolated local examples, not production license creation.

### MyShiftsView mobile initial focus

**Confirmed.** `initial-focus=reasonInput` forced focus to the textarea on open. The existing mounted focus test was changed to require the dialog heading and failed RED (1 failed / 7 passed) before the product fix. The dialog now targets a native `h2` with `tabindex=-1`, rendered through DialogTitle's template forwarding. This keeps the dialog named and initial focus inside without focusing an editable element. Users can Tab or tap into the reason field explicitly. The amended test passes; actual touch-emulated Chromium reports H2/noneditable with touch points enabled and confirms Tab containment, explicit textarea tap, Escape dismissal and return to the opener. This is evidence of noneditable initial focus, not a claim that an operating-system virtual keyboard was rendered and inspected. The production Chef demo account has no eligible shifts, so this conditional dialog is not claimed as exercised against production business data.

### HistoryView phone summary dividers

**Confirmed.** Actual 390px browser geometry before repair showed the three cards on one row but inline-start widths `[0,1,0]` and block-start widths `[0,0,1]`: the shared two-column phone selector removed the third divider and added a horizontal line. A small component-scoped rule now follows this component's always-three-column layout. Actual 390px and 1440px results are inline-start `[0,1,1]`, block-start `[0,0,0]`, all three Y coordinates equal. There is no global style fork or CSS-string unit assertion.
