新問題：修好 F16 讓一整類壞掉的錯誤路徑變成活的　#352

最低消費從「存不進去」變成「真的會擋單」之後， packages/database/src/services/order.ts:662 這段就從碰不到變成碰得到了。 追它怎麼變成 HTTP 回應時發現整條鏈路是壞的，而且不只這一條—— 這比 09-01 報告在 F18 附帶裡註記的「幣別硬寫成 RM」嚴重得多，那時只看到症狀的表面。

顧客金額沒到最低消費，收到的是 HTTP 500。 這個 throw new Error(中文字串) 穿過 OrdersService.ts:291-326 的 catch （只比對 6 個 sentinel）、穿過兩條路由的 catch（只比對 CLIENT_MUTATION_DUPLICATE）， 到 app-factory.ts:394 的全域處理器； ErrorSanitizer.sanitizeError 對不上任何分類器 （沒有 JWT／validation／constraint／not found 等字樣）， 落到 generic 分支 → 500、code: "GENERIC_ERROR"， 訊息則經 sanitizeMessage 原文放行。 諷刺的是同檔 :526 的 Restaurant not found 反而回對了 404—— 因為它碰巧含有 not found。現在的對錯是靠英文字串巧合，不是靠設計。

而且這是一整類，不是一個點。createOrder 裡有 5 條商業規則拒絕同樣落成 500： :580 餐廳未營業、:611 桌位不可用、:652 優惠券驗證失敗、 :662 最低消費、:838 缺貨。 （缺貨其實有對應的 mapper OrdersService.ts:98，但它只掛在改單路徑 :503／:574／:657，沒掛在 createOrder。） 另外 8 條是有正確轉譯的，所以要補的是缺口，不是新建管線。

幣別那半仍然成立，而且修法是現成的。 訊息把幣別硬寫成 RM（最低消費：RM${minOrderAmount.toFixed(2)}）， 而這家店的 settings.currency 是 TWD。 packages/utils/src/currency.ts 早就有 formatCurrency(amount, currency)（TWD／MYR／VND 的符號、位置、小數位都處理了）， packages/database 本來就依賴 @makanmasak/utils， 而 getMinimumOrderAmount 已經把 restaurant.settings 讀進來了—— 不需要新增任何管線。

唯一需要決定的是慣例：packages/database 裡有兩套互相矛盾的做法， 而且 coupon.ts:81-82 那條「packages/database 不能依賴 API 層的 ApiError」的註解 已經過期——ApiError 早就搬到 packages/utils， 同 package 的 ticket-primitives/state-machine.ts:43 與 reservation-state-machine.ts:43 已經在直接丟它， 而 apps/api/src/shared/utils/api-error.ts 是純 re-export， 所以全域處理器的 instanceof 會正確命中。 正是這個「要先選一套」讓它不符合本報告當初「不需要決策才直接修」的標準， 因此開成 #352 而不是逕自修掉。

F10a

沒有任何 UI 能建立「假別」，請假申請永遠送不出去

「申請請假」對話框的假別是必填，但下拉只有一個「請選擇假別」—— GET /leaves/{rid}/types 回 {"data":[]}，於是「送出申請」永遠是 disabled。

為什麼是死結而不是「還沒建資料」 production SELECT COUNT(*) FROM leave_types = 0。 後端有 POST /:restaurantId/types（限 ADMIN/OWNER）， 但 services/leavesService.ts 只有 getLeaveTypes / getBalances / getRequests / createRequest / approve / reject / cancel ——沒有 createLeaveType，任何 view 也沒有入口。 management-api、onboarding、scripts 全掃過，沒有任何地方會 seed 預設假別。

新租戶開站即死結：店主開不了假別，就永遠沒有人能請假，也就永遠沒有東西可以審核。

F10b

「初始化假期餘額」必定 400　已修

POST /api/v1/leaves/{rid}/balances/accrue   body: {"year":2026}
→ 400  VALIDATION_ERROR
   restaurantId: "Restaurant ID must be a valid UUID"  (invalid_type)

invalid_type 表示 zod 收到的是 undefined，不是格式錯。 路徑本身已經是 /:restaurantId/balances/accrue，handler 讀的也是 validatedParams.restaurantId——body 那一把從頭到尾沒有人用， 卻被 accrueLeaveBalancesSchema 列為必填。

同一份檔案裡就有正確寫法。validation.ts:113 的 createLeaveRequestSchema 明寫 restaurantId: restaurantIdString.optional(), // Injected by route handler from URL param， 就在 accrue 上方 48 行。
修法只有一種是對的：把 accrue schema 的 restaurantId 拿掉。 不要改成讓前端補送 body——那會造出第二個沒有經過 requireRestaurantAccess 把關的租戶來源，正是 #265 / #275 的形狀。
F8

出勤率與缺席的分母是全體在職員工，跟當天排班完全無關

// AttendanceOverviewTab.vue:162-166
const total   = employeeList.users.value.filter((u) => u.isActive).length;
const working = employeeList.stats.value.currentlyWorking;
const onLeave = employeeList.stats.value.onLeaveToday;
const absent  = Math.max(0, total - working - onLeave);
const rate    = total > 0 ? Math.round((working / total) * 100) : 0;
實測 我在排班總覽把 Demo Chef 排進 2026-09-01 的班，出勤總覽的數字完全沒變。 排出來的班表對這一頁沒有任何影響。

五人的店只排兩個人，另外三個休假的人會被算成紅字「缺席」，出勤率上限 40%。 而且 currentlyWorking 是「此刻在班」的瞬時值——打烊後任何店都是 0%， 卻掛在「出勤率」這個標籤下。
