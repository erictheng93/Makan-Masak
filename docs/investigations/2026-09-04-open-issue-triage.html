#311 · 付款狀態詞彙分裂已修並上線

issue 的修法方向正確，但範圍要擴大兩處，同時有一個好消息。

現況是三套詞彙在打架（2026-09-04）

層詞彙
正規型別 ORDER_PAYMENT_STATUSESpending · completed · failed · refunded
實際寫入（3 個服務）pending（預設） · paid · refunded · partial_refunded
守衛（防重複付款／退款）paid · completed · refunded · partial_refunded

completed 與 failed 在全 repo 都沒有任何寫入點。宣告的四個值裡有兩個是空的，而真正會寫的兩個不在集合裡。

issue 漏掉的兩處

  • 第三個寫入點。pos/services/MarketCheckoutPOSPaymentService.ts:339 也把 "paid" 寫進 orders 表。issue 只點名了 PaymentService 的兩處。
  • partial_refunded 同樣不在正規集合。refundPayment.ts:102 部分退款時寫這個值，讀回來一樣變成 pending——與 paid 完全相同的故障，只是走另一條路。
好消息：不需要動任何守衛。三個守衛都已經同時接受 paid 與 completed—— payableGuard 的 NOT IN ('paid','completed','refunded','partial_refunded')、 isAlreadyFinalized 的同名清單、refundPayment 的負向清單 NOT IN ('pending','failed','cancelled','refunded')。 收斂到 completed 是三個字面值 + 一個型別的改動，不碰控制流。
複驗（09-09）：兩處擴大範圍都被採納了。用本節下方那支掃描重跑，現在 .update(orders) 帶 paymentStatus 的三個非測試寫入點 （PaymentService.ts:432、:451、MarketCheckoutPOSPaymentService.ts:339） 全部寫 "completed"，ORDER_PAYMENT_STATUSES 也補進了 partial_refunded。 多做的一件事是沒有直接刪掉 "paid"：路由層留了一張 PAYMENT_STATUS_ALIASES = { paid: "completed" }，而恆等那一半是從 ORDER_PAYMENT_STATUSES 推導、不是手抄——因為這裡的後備是靜默的 "pending" 而不是報錯，手抄清單漏一個值不會失敗，只會安靜地用錯的狀態過濾。那正是 partial_refunded 當初出事的方式。

時間成本那一條也兌現了：production 今天仍是 7 筆訂單、payment_status 全為 pending（3 cancelled / 3 pending / 1 delivered），零筆需要 backfill。

不要一起改的

pat = re.compile(r"\.update\(\s*orders\s*\)(.{0,700}?)\.where", re.S)

#310 · 付款狀態在後台無路可寫仍開著

三項主張全部複驗成立，另外找到一個讓它「看起來有覆蓋」的假象。

updatePaymentStatusSchema 其實已經寫好了（validation.ts:184），只是沒有任何路由掛它。所以連請求驗證都備好了，差的只有端點與實作。

它的測試鎖住了空殼。OrdersService.test.ts 斷言的是 「回傳的 order id 是 42」與「快取被清掉」，完全沒有斷言付款狀態有被寫入任何地方。 所以這兩個測試在一個什麼都不做的空殼上是綠的，方法看起來有覆蓋。

可以先切出來的一項

前端 canCancel 只允許 pending/confirmed，但伺服器的 ORDER_STATUS_TRANSITIONS 允許 preparing → cancelled 與 ready → cancelled——前端比後端更嚴。這一項不依賴 #311，是純前端判斷式放寬，可獨立成一個 commit，而且是三項裡最直接影響店主日常的：客人中途走人時，目前只能把單一路推到 paid，那正是「進死路」的入口。

已修的（都已上線）：
  • 收銀台走真的付款端點。e66896b3：CashierView 原本打 PUT /orders/:id/status 再打一個後端根本不存在的 /pos/quick-payment， 404 被 catch {} 吞掉。改走 POST /api/v1/payments，一次寫齊交易列、 payment_status、payment_transaction_id，並帶跨重試共用的 Idempotency-Key。
  • canCancel 改成推導而非抄寫。717a9b36：ORDER_STATUS_TRANSITIONS 搬進 packages/shared-types，新增 CANCELLABLE_ORDER_STATUSES，前端／API／database 三邊都推導。 順帶補上前端缺的角色檢查——這個畫面也服務廚師／送菜／收銀，按鈕本來對他們渲染、點下去必 403。
還沒修的（issue 因此仍開著）：
  • getNextStatus 仍有 delivered: "paid"（OrdersView.vue:1020）。 issue 的第 1 點建議是讓「更新」在 delivered 停住，沒有做。所以那條「按出來的 paid」的路徑還在。
  • 營收仍計入手按的 paid。analytics.ts:51 的 FULFILLED_ORDER_STATUSES 仍是 ["paid","delivered","served"]。 #312 修掉的是已取消訂單被計為營收，不是這一條。
  • canRefund 仍要求 paymentTransactionId（:893）。 收銀台修好之後，正常收款的單有這個欄位了，所以退款鈕會出現；但手按到 paid 的單沒有，仍是死路。

那個假綠燈只被修掉一半。#311 拿掉了測試裡的 "paid" as never 轉型 （現在是型別正確的 "completed"），但斷言一字未改： 仍然只有 toMatchObject({ id: "42" }) 與快取被刪。 型別現在對了，覆蓋率的假象原封不動。真要收掉這一條， 要嘛刪掉方法，要嘛給它一個斷言「有東西被寫進去」的測試。

殘餘部分的驗收條件

  • 把 delivered: "paid" 放回去 → 專門測「更新鈕在 delivered 停住」的測試必須轉紅。
  • production 上 SELECT COUNT(*) FROM orders WHERE status='paid' AND payment_transaction_id IS NULL 必須維持 0。今天是 0（線上根本沒有 paid 訂單），所以這是潛伏而非發生中——但它也表示這一條目前沒有真實資料在惡化，可以慢慢決定。

#312 · 數據分析已修並上線

實際是三個缺陷，不是兩個。而且修法有一個很容易做錯的細節。

totalOrders 絕對不能一起加過濾。它是轉換率的分母 （completedOrders / totalOrders）。順手一起過濾，分子分母變同一個集合， 轉換率永遠是 100%。正確做法是把一個查詢拆成兩個： A 不過濾出 totalOrders，B 過濾出 totalRevenue + averageOrderValue。 AOV 必須與營收同一個查詢，否則會算成 570/7 而不是 570/4。

缺陷二：不只「本月」，每一個期間都是滾動視窗

這對三張未結的效能 issue 各有不同意義：

  • #323（冷啟動地板）：它引用的「/info 150ms–1.1s」大部分不是 Worker 的成本。 扣掉握手之後 /info 穩定在 ~137ms，而那還含到邊緣的網路往返。 要先把量測改成 keep-alive，否則一直在測 TLS。
