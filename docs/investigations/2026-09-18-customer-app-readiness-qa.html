09-18 結論：各流程能不能上線

流程判定理由
點餐主流程 有條件 桌位 QR → 菜單 → 購物車（數量、品項備註、訂單備註、姓名、電話）→ 送出，在 production 全部通過。 但店家公開碼（shop mode）的內用單在 production 100% 送不出去（R1，本輪已修、尚未部署）； 訪客優惠券仍會被靜默丟棄（#382，上線前不要對訪客發券）。
訂單追蹤 可上線 確認 → 製作中 → 準備完成 → 已送達 → 現金結帳，每一步都不重整即時到頁，時間軸五格都有時間； 訪客自己取消只出現一則 toast。已知風險：加點後前一筆追蹤頁 403（#383，重測仍成立）、 service worker 讓回訪顧客整趟跑上一版前端（R3 / #395），後者也決定了本輪修正多快能到顧客手上。
座位與預約 有條件 候位的叫號與確認抵達即時可用，但取號後畫面被通知權限詢問卡住、票號既不顯示也沒保存（R7，本輪已修、尚未部署）。 線上訂位在顧客端不存在，而其公開寫入端點仍開著（#385）。 預約服務可建立、查詢、取消，但顯示「待付款」卻沒有任何付款途徑或說明（R9 / #398）。
揪團與夜市市集 不可上線 揪團能把合併的單送進廚房，但送出後團主與團員都看不到任何結果或追蹤入口（R5 / #396）， 回菜單立刻加的菜會掉進被隱藏的個人購物車（R4，本輪已修），正常來回幾次就被限流 429（R6 / #397）。 跨攤結帳在 production 從建立那一步就被 CSRF 擋下（R13 / #401），而擋在後面的「付款」不經任何金流就把每一攤的訂單記為已付款（R2 / #400）—— 兩者必須一起修，先修 CSRF 等於打開付款的洞。市集在 production 0 筆。 代幣（儲值）功能在 production 由旗標關閉。

對上線的意義：掃碼點餐的一次造訪就是一整餐，所以每次部署，回訪顧客晚一整餐才拿到。 這一輪與前兩天部署的每一個顧客端修正（追蹤頁即時更新、訪客自己取消、以及本輪的 R1／R4／R7）都受這個延遲約束。 同一個 runtimeCaching 規則還把帶 guest token 的 GET /guest-orders/:id 在裝置上快取 24 小時， 網路失敗時會靜默顯示舊的訂單狀態。

沒有直接修：service worker 改錯會讓已安裝的客戶端卡在壞版本、而且很難遠端救回， 需要在 preview 環境用兩次 build 驗證，不適合順手改。issue 內附完整修法與驗收步驟。
