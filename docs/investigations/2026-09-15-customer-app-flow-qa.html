C1

訪客套用優惠券後，購物車顯示折扣後金額，實際建立的是原價訂單

#382

在 production 臨時建一張 NT$20 定額券（QA0915COUPON，事後已刪）， 掃桌位 QR 以訪客身分套用，然後送出。

CartView.vue:1100 依 !isAuthenticated && isDineIn 分兩條送出路徑。 已登入那條（:1124-1136）帶 couponCode； 訪客那條（:1102-1116）沒有。而總計是前端自己算的（:841）， 所以折扣只存在於畫面上。

再往下一層，POST /api/v1/guest-orders 的 schema 根本沒有 couponCode 欄位—— 這不是漏送一個參數，是訪客訂單從來就不支援優惠券，但購物車對訪客顯示了完整的優惠券 UI， POST /coupons/validate 也真的會回 200 並算出折扣。

掃 QR 免登入下單是顧客端的主路徑，所以受影響的是絕大多數訂單。 production 目前 coupons 表 0 筆，所以還沒有人被咬到——但那是「沒有資料」，不是「沒有問題」。

沒有直接修，是因為有兩條都說得通的路要先選一條（讓 guest-orders 支援優惠券， 或在訪客路徑隱藏優惠券 UI），而 usage_limit_per_user 對沒有身分的訪客要用什麼當 key 需要決定。細節與建議寫在 issue 裡。

C5

店家公開碼路徑：選了「內用」顯示「外帶」，購物車只給外帶與外送

本輪已修

這家店的設定是 enableDineIn: true, enableTakeaway: false, enableDelivery: false。走 shop mode：

  1. /shop/order-type 只提供「內用」—— 正確，它讀的是店家設定
  2. 選內用後進 /shop/menu?fulfillmentType=dine-in，標頭徽章顯示 「🛍️ 外帶」
  3. 打開購物車，「取餐方式」只有 外帶 與 外送，沒有內用
  4. 點「外送」會展開外送地址／聯絡電話表單 —— 而同一畫面上就寫著「這間店目前沒有公開的預約、外送或現場服務」

兩個獨立的根因：

  • 徽章（ShopMenuView.vue）是三值當兩值的三元式： delivery ? 外送 : 外帶。store 的 fulfillmentType 有 "dine-in" | "takeaway" | "delivery" 三個值，dine-in 掉進 else。
  • 購物車選項（ShopCartModal.vue）：外帶按鈕完全沒有守門； 外送的守門是 fulfillmentType === "delivery" || shopCartStore.deliveryFee >= 0， 而 deliveryFee 預設 0，0 >= 0 恆真 —— 這個守門是空的。 內用則根本沒有按鈕。
修法 兩者都改成讀店家自己的開關，也就是 OrderTypeLandingView 一直在用的那一組 restaurants.settings.enableDineIn / enableTakeaway / enableDelivery。 ShopMenuView 把三個布林當一個 fulfillment prop 傳給購物車， 購物車據此決定顯示哪幾顆按鈕。徽章改成三分支。 這樣購物車就不可能提供落地頁拒絕顯示的取餐方式。

訪客 token 是一單一 token：KV 裡存的 guest_token:<token> 帶著 orderId， middleware/guestAuth.ts:54-58 會比對路由參數，不符就 forbidden ACCESS_DENIED。而前端只存一把 localStorage["guest_auth_token"]，第二筆訂單直接覆蓋第一筆。

「繼續點餐」就在追蹤頁上，加點又是內用最常見的行為 —— 這條路徑是應用程式自己引導顧客走進去的。

對照組很說明問題：同一頁的即時連線 token 早就是按訂單分鍵的 （makanmakan_guest_realtime_token:<restaurantId>:<tableId>:<orderId>）， 只有 API token 不是。

沒有直接修，是因為讀取點是 services/api.ts:102 的 axios 攔截器—— 顧客端每一個請求都會經過它。改成分鍵要讓攔截器知道「這個請求是為哪一張單發的」， 不是能順手改掉的地方。建議修法（保留預設那把、另加 guest_auth_token:<orderId>）寫在 issue 裡。

順帶一提，那個畫面把例外類別名稱 ApiException: 原文印給顧客看。 沒有單獨開 issue，因為修掉 #383 之後這個畫面本來就不該出現。

C12

即時更新只換狀態不帶時間戳，時間軸的時間要重整才會出現

本輪已修

這是上一條在實測時先浮現的症狀：推完整條狀態鏈之後， 時間軸五格全部沒有時間；按下重整，除了「正在製作」以外全部出現。 兩件事疊在一起，所以要分開。

根因 handleWebSocketMessage 用 queryClient.setQueryData 往快取的訂單上打一個 patch，而那個 patch 只有 status 與 updatedAt。 時間軸要讀的四個 *At 從頭到尾是 undefined， 除非顧客剛好重整。

修法是在 patch 之後 invalidateQueries({ queryKey: ["order", orderId] })， 讓畫面上的訂單回到伺服器的版本，而不是本地拼出來的版本。 一張單最多五次 refetch，代價可以忽略。

C14

註冊失敗顯示「登入失敗」

本輪已修

上面那個 503 在畫面上長這樣：登入失敗。在註冊頁。

// apps/customer-app/src/stores/auth.ts:57（修正前）
const failureMessage = (_err: unknown): string => t("auth.loginFailed");

一句寫死的文案，被 requestOtp / verifyOtp / loginWithPassword / register 四個動作共用， 而且參數叫 _err —— 錯誤內容從頭到尾沒有被看過。 RegisterView 那邊其實寫對了 （result.error || t("auth.registerFailed")），是 store 先把錯的字串塞進 result.error。

修法是讓 failureMessage 收一個 fallback key，register 傳 auth.registerFailed（該 key 本來就存在）。 其餘三個動作屬於登入流程，維持原文案。

「驗證通道沒設定」這種重試永遠不會成功的失敗值不值得一句專屬文案，是文案決定，留在 #384。

一個誤判，記下來

實測中一度認定「shop 購物車送出失敗時完全沒有任何回饋」，理由是連續兩次 429 之後畫面上找不到任何錯誤訊息。

那是錯的。toast 的顯示時間約 3 秒，而我當時是送出後等 6 秒才截取畫面文字 —— 量測窗口整個錯過了 toast。改成每 0.7–0.9 秒取樣一次之後，訊息清楚出現： 「您在此餐廳已有進行中的訂單，請等待完成後再送出新訂單。」 ShopCartModal 的錯誤管線是完整的 （utils/order-submit-error.ts 有一張 30 多個 code 的對照表）。

教訓：短生命週期的 UI 回饋要用取樣頻率高於其生命週期的方式量測， 否則「沒看到」會被讀成「沒有」。這一條沒有進摘要表，因為它不是發現。
