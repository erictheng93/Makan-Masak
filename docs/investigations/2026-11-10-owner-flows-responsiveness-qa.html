I1

菜單圖片每張約 2 秒，每次瀏覽都重讀 R2

已修復

images.makanmasak.com 是直接掛在網域上的 Worker，而這種 Worker 位在 Cloudflare 快取前面。所以每次瀏覽每張圖都會重跑 Worker、重讀 R2，連 16 KB 的縮圖也要 0.6–1 秒；回應雖然標了 immutable，但 edge 從來沒有存過。

未驗證與後續

  • F2 的第二次清除只有自動測試證明；它防的是顧客恰好和店主同時讀菜單，線上無法穩定重現。
  • 儲存設定修改後重新量測仍要 1.2 秒（有「儲存中」狀態），同一台伺服器更新桌台只要 0.5 秒；要先拿到伺服器端分段計時才能決定怎麼改。
  • 座位模式（一座位一 QR）沒有測試。
  • I1 刪圖時清 edge 副本沒有自動測試；它只清處理刪除的那個資料中心，其他地方要等 1 天過期。
  • N2 的 focus 外框是推測的原因，還沒在真實瀏覽器確認。
  • 其他裝置讀菜單：廚房顯示不讀菜單；管理端的讀取都帶登入憑證，本來就略過 edge 快取，只有內層查詢快取在清除生效前約 1 秒可能是舊的。
  • R1 的根因是推論，沒有逐步追到；兩條實測路線都沒再重現，但沒有從每一頁出發試過。
  • Staging 不能證明 production 安全：staging 的資料庫由新基線建立，production 由舊的 migration 系列建立，兩者仍有差異；正式 migration 前仍要在 production 結構的副本上預演。
  • 整體 API 延遲：staging 上登入 2.2–2.5 秒、開班 2.1 秒、收款 3.2 秒、送出退款 3.5 秒、顧客送單 3.35 秒（原 6 秒）。每個需登入的請求都先付驗證（約 0.4–0.5 秒）與模組檢查（約 0.2–0.4 秒）的依序等待；這兩段影響所有頁面，值得下一輪處理。
  • POS 其他小問題：選「全額退款」不會自動帶入金額；班次標題顯示原始 ID（01a1c5cf-…）而非可讀名稱；收款成功、退款等對話框沒有 role="dialog"；退款送審後沒有走查店主核准的步驟。
  • 訪客訂單需要店員先接單才會出現在廚房（廚房只顯示已確認的訂單）。這是現有設計，但店家若沒人盯訂單頁，顧客會一直等；要不要自動確認是產品決定。
  • 無聲錯誤的基準：仍有 134 處只寫 log 的 catch 待逐步改掉。
  • 停用優惠券沒有確認步驟，誤觸立即生效；要不要加是產品決定（停用收銀機已可復原）。
  • 店家登入：重設密碼信件的連結不帶店家代碼（頁面會改用這台裝置記住的店家）；在兩個 /s/ 連結之間切換而不重新整理時，頁面仍顯示第一家店；本機種子資料的店家沒有店家代碼。
  • L2 的鎖定隔離以真 D1 整合測試驗證；為了不影響真實帳號，沒有在 production 對真實帳號輸入錯誤密碼。
