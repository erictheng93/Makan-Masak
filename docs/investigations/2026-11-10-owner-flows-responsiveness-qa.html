結論摘要

走查共找出 13 個點擊後反應不良的地方，最嚴重的是新增菜品要等 5.7 秒、期間畫面完全沒有回饋，店主很可能重按而建出重複菜品。根因分兩層：前端寫入時沒有載入狀態、也不做樂觀更新；後端每次菜單寫入都要等快取清除、搜尋索引同步、即時推播全部跑完才回應。

兩層都已修好並上線。現在每個按鈕都在 0.1 秒內有回饋，新增菜品伺服器回應 0.44 秒，顧客端菜單約 2.5 秒內反映店主的修改。修復過程另外發現並處理了 3 個問題：刪掉的菜在管理畫面又冒出來、顧客可能把舊菜單寫回快取，以及改價／刪菜從來沒有清掉顧客端的外層快取。最後一項早在這次修改之前就存在。

M6

根因：菜單寫入要等快取、搜尋、推播全部做完才回應

已修復

桌台寫入在同一個 Worker 只要 0.3–0.6 秒，菜單寫入卻要 1.6–5.7 秒。每次寫入都依序等待：搜尋索引同步、即時推播，以及兩層快取（packages/database 的查詢快取、edge 快取）的 tag 清除。每次 tag 清除都是好幾趟 KV 往返，每趟 0.2–0.4 秒。

修復 第一步：搜尋同步與推播移到 waitUntil（fc16aee15），新增菜品從 5.7 降到 4.1 秒。
第二步：快取清除也改成回應之後才做，但順序固定：先清查詢快取，再清 edge 快取，最後才推播（5303691a0）。這個順序保證收到「菜單已變更」的客戶端重抓時，兩層快取都已經清掉。店主自己的重抓帶 Cache-Control: no-cache，兩層快取都會略過；同一請求內在清除完成前的快取讀取，則直接讀 D1。
取捨回應後才清快取，代表顧客可能在店主存檔後約 1–2 秒內還看到舊菜單。實測顧客端約 2.2–2.5 秒反映變更。

修復過程中新發現的問題

F1

刪掉的菜在管理畫面又冒出來

已修復

M6 讓推播排在快取清除之後，所以會晚一點到。實測時下架的推播在刪除期間才到達，它觸發的背景重抓帶回刪除前的菜單，蓋掉了本地的刪除。伺服器端實際上已經刪掉。

修復重抓期間如果自己有寫入開始或結束，丟掉這次結果再抓一次（103c5367c）。回歸測試在沒修時失敗、修了通過。
驗證下架後 0.7 秒內刪除：0.6 秒從畫面消失，之後 8 秒都沒有再出現。
F2

顧客讀菜單時可能把舊菜單寫回快取

已修復

有兩種情況。一是顧客在清快取的空檔讀菜單，從還沒清的查詢快取拿到舊資料，再存回已經清過的 edge 快取；二是顧客在寫入生效前讀了 D1，結果在清除之後才存進查詢快取。兩種都會讓舊菜單最多再留 5 分鐘，例如已下架的菜顧客還點得到。這兩個競態在這次修改前就存在、時序也相同，但一直沒有防護。

修復每次延後的清除在 3 秒後重跑一次，先查詢快取、再 edge 快取（4fa04afe7）。測試模擬顧客在第一次清除後寫回舊菜單：沒有第二次清除時失敗，有時通過。
F3

改價、改名、刪菜從來沒清顧客端的外層快取

已修復

edge 快取只依網址裡的餐廳 ID 決定清哪一間，但有 10 條寫入路由的網址沒有餐廳 ID（/menu/items/:id、/categories/:id、選項群組、選項等），只有上下架另外走了清除路徑。結果顧客最多 5 分鐘看到舊價格。這是早就存在的問題。

修復每條菜單寫入在清查詢快取時都帶 restaurant:{id} tag（已逐一確認），現在記錄下來，edge 清除也涵蓋這些餐廳（78d262c56）。
驗證改價 150 → 168，顧客端菜單 2.2 秒內變成 168。
