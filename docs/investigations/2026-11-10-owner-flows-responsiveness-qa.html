M6

根因：菜單寫入要等快取、搜尋、推播全部做完才回應

已修復

桌台寫入在同一個 Worker 只要 0.3–0.6 秒，菜單寫入卻要 1.6–5.7 秒。每次寫入都依序等待：搜尋索引同步、即時推播，以及兩層快取（packages/database 的查詢快取、edge 快取）的 tag 清除。每次 tag 清除都是好幾趟 KV 往返，每趟 0.2–0.4 秒。

修復 第一步：搜尋同步與推播移到 waitUntil（fc16aee15），新增菜品從 5.7 降到 4.1 秒。
第二步：快取清除也改成回應之後才做，但順序固定：先清查詢快取，再清 edge 快取，最後才推播（5303691a0）。這個順序保證收到「菜單已變更」的客戶端重抓時，兩層快取都已經清掉。店主自己的重抓帶 Cache-Control: no-cache，兩層快取都會略過；同一請求內在清除完成前的快取讀取，則直接讀 D1。
取捨回應後才清快取，代表顧客可能在店主存檔後約 1–2 秒內還看到舊菜單。實測顧客端約 2.2–2.5 秒反映變更。

菜單圖片

I1

菜單圖片每張約 2 秒，每次瀏覽都重讀 R2

已修復

images.makanmasak.com 是直接掛在網域上的 Worker，而這種 Worker 位在 Cloudflare 快取前面。所以每次瀏覽每張圖都會重跑 Worker、重讀 R2，連 16 KB 的縮圖也要 0.6–1 秒；回應雖然標了 immutable，但 edge 從來沒有存過。

修復 第一次讀取後，Worker 把每個尺寸的圖存一份在 Cloudflare edge（caches.default），之後直接從 edge 回應，不碰 R2（3cdf81363）。 edge 副本 1 天過期，所以刪掉的圖最多一天內各地都停止提供；瀏覽器端仍維持一年快取。刪圖時也會清掉 edge 副本，但只清處理刪除的那個資料中心。
驗證用空的瀏覽器快取同時載入 Demo 小館的 8 張菜單圖：Worker 每張從 137–354 ms 降到 4–12 ms，每張 0.65–0.86 秒，8 張共 0.86 秒（修復前每張約 2 秒）。
剩下的時間主要花在下載約 830 KB 的 JPEG 和網路往返。Demo 小館的圖是舊的 JPEG；新上傳的圖已經編成 WebP（useImageUpload.ts），檔案會比較小。每個資料中心第一次讀某張圖時，仍要從 R2 讀（95–354 ms）。

H1

店主總覽的健康面板在系統異常時反而失敗

已修復

API 包裝層用一份已知的 axios 選項名單，判斷第二個參數是請求設定還是查詢參數，validateStatus 不在名單上。所以總覽的健康檢查被送成 ?validateStatus=e=>e<400||503==…，而系統處於嚴重狀態時伺服器回 503，頁面把它當錯誤，健康報告顯示不出來。其他用到 validateStatus 的地方都不走這個包裝，沒有受影響。

修復把 validateStatus 加進名單（2acec86fa）。測試確認它作為請求設定傳給 axios，一般物件仍當查詢參數。
驗證production 的健康請求網址不再帶 validateStatus。實際的 503 嚴重狀態無法在線上製造，只有自動測試涵蓋。

店主總覽所有數字等最慢的健康檢查

已修復

總覽一次等 7 個請求全部完成才結束載入，最慢的是健康檢查（約 1.7 秒），店主最少看的也是它。

R1

進菜單頁時即時連線重連

已修復

進菜單時頂端徽章會變成「Connecting／Reconnecting」，重新要一次連線 token，連上後菜單再整份下載一次。根因（推論）：儀表板首頁的通知面板在離開時，呼叫了整個 app 共用的即時連線的 disconnect()，下一頁只好重連；菜單頁又在每次連上時都重抓。

已修復

  • 儲存設定修改後重新量測仍要 1.2 秒（有「儲存中」狀態），同一台伺服器更新桌台只要 0.5 秒；要先拿到伺服器端分段計時才能決定怎麼改。
  • 座位模式（一座位一 QR）沒有測試。
  • I1 刪圖時清 edge 副本沒有自動測試；它只清處理刪除的那個資料中心，其他地方要等 1 天過期。
  • N2 的 focus 外框是推測的原因，還沒在真實瀏覽器確認。
  • 其他裝置讀菜單：廚房顯示不讀菜單；管理端的讀取都帶登入憑證，本來就略過 edge 快取，只有內層查詢快取在清除生效前約 1 秒可能是舊的。
  • R1 的根因是推論，沒有逐步追到；兩條實測路線都沒再重現，但沒有從每一頁出發試過。
  • 還沒走查的店主流程：處理訂單、POS 結帳、員工管理、優惠券。這些是每天點最多的地方，值得再走一輪。
