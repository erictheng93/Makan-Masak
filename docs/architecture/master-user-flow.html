流程說明

  • 訪客可瀏覽公開資訊；掃描桌位／座位 QR 亦可免登入下單，登入僅用於歷史訂單、優惠與會員權益。
  • 六個角色（0 管理者／1 店主／2 廚師／3 送菜／4 收銀／5 顧客）共用同一組 JWT，前端依 role 分流到不同門戶與路由。
  • 訂單事件經 Durable Object 廣播，同時到達廚房顯示、送菜清單、收銀台與顧客追蹤頁，四端看到的是同一份狀態。
  • 金流結果由金流商 webhook 回寫；夜市跨攤結帳另走 market-checkouts，付款一次、分帳逐攤。
  • 租戶／授權／部署屬控制平面，由獨立的 Management API 承接，與各店營運 API 分開部署。
  • 系統由哪些東西組成、每個 Worker 綁了什麼資源，見 系統架構圖。
  • 每一條流程的逐步細節與 edge cases 寫在 docs/flows/；四張細節圖：點餐、訂單狀態鏈、收款與退款、市集跨攤結帳。

主要資料流向（範例）

  • 顧客付款 → 第三方金流 → webhook 回調 → 訂單 payment_status = completed
  • 系統通知 → Email／OTP／Web Push → 顧客與各角色
  • 訂單事件 → Durable Object → 廚房／送菜／收銀／顧客追蹤
  • 菜單異動 → Queue fan-out → FTS5 全文索引 ＋ Vectorize 向量重建
  • 每日排程 → D1 匯出 → R2 備份保存 ／ 異常 → Slack 告警

備註（容易踩到的四件事）

  • 店家 QR 是公開識別碼，不是憑證。GET /api/v1/restaurants/:id 會直接回傳它，任何人都拿得到。它只用來辨識「這是哪一家店」以及「手上的貼紙是不是現行版本」，不可當作到店證明。
  • 桌位／座位 QR 則帶 HMAC 簽章（buildSignedQRUrl），性質與店家 QR 完全不同，不要把上一條的結論套用到它們身上。
  • 金額一律以「分」為單位的整數儲存，時間戳一律 INTEGER Unix 毫秒；新資料表一律建為 STRICT，否則 SQLite 會靜默把 TEXT 塞進 INTEGER 欄位。
  • 訪客點餐的濫用防護以（餐廳, IP）為 key，疊在全域 per-IP 限流之下。不可把全域限流器改成以餐廳為 key——那會讓攻擊者的額度乘上餐廳數量。
